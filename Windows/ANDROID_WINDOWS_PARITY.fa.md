# تطبیق Android و Windows با هدف اصلی V2rayWatch

## تعریف محصول

V2rayWatch باید دو قابلیت جدا اما مکمل داشته باشد:

1. **پایش لینک‌ها (Link Monitoring):** کاربر چند لینک/کانفیگ را وارد می‌کند. برنامه هر لینک را مستقلاً از مسیر پروکسی همان کانفیگ آزمایش می‌کند؛ مثلاً هر ۲۰ ثانیه. اگر چند آزمایش پیاپی ناموفق بود، لینک را قطع‌شده علامت می‌زند و هشدار می‌دهد. هنگام برگشت اتصال هم اعلان بازیابی می‌فرستد.
2. **اتصال دستگاه (VPN / System Proxy):** کاربر در صورت نیاز یک پروفایل را برای ترافیک خود دستگاه انتخاب می‌کند و System Proxy یا TUN را فعال می‌کند.

این دو نباید با هم اشتباه شوند. پایش سلامت یک لینک نباید تنظیم System Proxy/TUN ویندوز را تغییر دهد یا ترافیک همهٔ برنامه‌ها را از آن لینک عبور دهد.

## بررسی Android 0.2.1

سورس Android در فایل `V2rayWatch-project-0.2.1.zip` قرار دارد. README فارسی و انگلیسی و کلاس‌های `XrayDelayTester`، `MonitorService` و `NotificationHelper` بررسی شدند.

| قابلیت | پیاده‌سازی Android |
|---|---|
| افزودن لینک | تک‌لینک و چندلینک، Subscription از HTTPS، Android Share، QR و Xray JSON |
| پروتکل‌ها | VLESS، VMess، Trojan، Shadowsocks، Hysteria2 / hy2 |
| تست واقعی | برای هر پروفایل یک Xray Core موقت با JSON همان پروفایل راه‌اندازی می‌شود؛ سپس `CoreController.measureDelay(url)` از داخل outbound همان پروفایل درخواست HTTPS می‌فرستد. این TCP ping یا تست پورت نیست. |
| آدرس تست | پیش‌فرض `https://www.google.com/generate_204` و fallback برابر `https://www.gstatic.com/generate_204`؛ هر دو قابل تنظیم‌اند. |
| پایش پس‌زمینه | Foreground Service با اعلان دائمی؛ شروع و توقف توسط کاربر |
| فاصلهٔ تست | UI نسخهٔ فعلی گزینه‌های ۲۰، ۳۰، ۶۰ و ۱۲۰ ثانیه را معرفی می‌کند؛ تنظیمات Repository مقدار ۲۰ تا ۳۶۰۰ ثانیه را نگه می‌دارد. |
| تشخیص قطعی | آستانهٔ خطای متوالی قابل تنظیم، پیش‌فرض ۲ و محدود به ۱ تا ۵ |
| هشدار | اعلان هنگام تغییر وضعیت به قطع‌شده و هنگام بازیابی |
| ذخیره‌سازی | لینک‌ها با AES-GCM و کلید Android Keystore رمز می‌شوند. |
| اتصال کامل دستگاه | ندارد؛ Android این نسخه صرفاً ابزار پایش است و TUN/VPN سراسری ایجاد نمی‌کند. |

### نکات مهندسی Android

- حداکثر دو Core تستی هم‌زمان اجرا می‌شوند.
- در هر دور ابتدا همهٔ پروفایل‌ها بررسی می‌شوند و دور بعدی تا پایان دور فعلی شروع نمی‌شود؛ مدت واقعی دور می‌تواند از فاصلهٔ اسمی بیشتر شود، به‌ویژه وقتی تعداد زیادی لینک timeout شوند.
- هر تست می‌تواند URL اصلی و سپس fallback را امتحان کند؛ بنابراین زمان یک پروفایل ناموفق می‌تواند از ۲۰ ثانیه بیشتر شود.
- Foreground Service و اعلان دائمی برای پایش پیوسته استفاده شده است. محدودیت باتری سازندهٔ گوشی همچنان می‌تواند اجرای دقیق هر ۲۰ ثانیه را به تأخیر بیندازد.
- اگر VPN دیگری در Android فعال باشد، ممکن است ترافیک خود تست هم از آن عبور کند؛ در نتیجه باید نتیجه را با توجه به مسیر واقعی دستگاه تفسیر کرد.

## بررسی Windows فعلی

Windows روی سورس v2rayN 7.25.6 بنا شده و دو رفتار متفاوت دارد:

### ۱. تست دستی سلامت پروفایل

دکمهٔ `ProfilesViewModel.FastRealPingCmd` در نسخهٔ upstream به `ServerSpeedtest(ESpeedActionType.FastRealping)` می‌رسد. این فرمان:
- فهرست پروفایل‌های موجود را برای تست برمی‌دارد، نه فقط پروفایل فعال سیستم را.
- برای هر پروفایل Core موقت مناسب (Xray یا sing-box) را با `CoreManager.LoadCoreConfigSpeedtest` آماده می‌کند.
- از SOCKS محلی همان Core درخواست HTTP تست را با `ConnectionHandler.GetRealPingTime` ارسال می‌کند.
- پس از تست، Core موقت را متوقف می‌کند.

بنابراین این قابلیت تست واقعی outbound هر پروفایل است و برای اجرای آن لازم نیست System Proxy یا TUN فعال باشد. در نسخهٔ داشبورد فعلی، این آزمایش **دستی** است و نتیجهٔ تأخیر را در جدول پروفایل‌ها نشان می‌دهد.

### ۲. اتصال واقعی ترافیک Windows

- انتخاب پروفایل پیش‌فرض، پروفایل فعال موتور v2rayN را تعیین می‌کند.
- System Proxy ترافیک برنامه‌های سازگار ویندوز را به پراکسی محلی هدایت می‌کند.
- TUN ترافیک شبکهٔ ویندوز را از مسیر تونل موتور عبور می‌دهد و به مجوز Administrator و درایور مربوط نیاز دارد.

این بخش یک کلاینت اتصال واقعی است؛ ولی معادل پایش همهٔ لینک‌ها نیست.

### وضعیت جدید پایش دوره‌ای در Windows

در شاخهٔ توسعهٔ فعلی، شکاف بالا با یک پیاده‌سازی اولیه رفع شده است:

- دکمهٔ شروع/توقف پایش در نوار بالای داشبورد
- فاصله‌های قابل انتخاب ۲۰، ۳۰، ۶۰ و ۱۲۰ ثانیه؛ پیش‌فرض ۲۰ ثانیه
- آستانهٔ ۱، ۲ یا ۳ شکست متوالی؛ پیش‌فرض ۲
- اجرای `ProfilesViewModel.ServerSpeedtest(ESpeedActionType.FastRealping)` با token لغو و صف انحصاری؛ دورهای پایش روی هم نمی‌افتند.
- هر نتیجهٔ Real Ping از موتور upstream به یک وضعیت سلامت مجزا تبدیل می‌شود: Connected / Unstable / Disconnected / Not testable
- ثبت آخرین زمان بررسی در ردیف پروفایل
- اعلان System Tray فقط هنگام انتقال به Disconnected و اعلان بازیابی هنگام برگشت به Connected
- نتایج تست دستی به دور پایش تزریق نمی‌شوند؛ مجموعهٔ پروفایل‌های هر دور در لحظهٔ شروع snapshot می‌شود تا لینک تازه‌اضافه‌شده قبل از اولین تست، قطع‌شده محسوب نشود.
- تنظیمات فاصله و آستانه در `%LOCALAPPDATA%\\V2rayWatch\\monitor-settings.json` ذخیره می‌شوند.
- پایش از Real Ping واقعی v2rayN استفاده می‌کند و به System Proxy یا TUN وابسته نیست.

**محدودیت‌های مهم:** پایش با شروع صریح کاربر فعال می‌شود؛ تا وقتی فرایند برنامه باز است (از جمله حالت System Tray) اجرا می‌شود، اما پس از خروج کامل از برنامه یا reboot به‌طور خودکار سرویس‌دهی را ادامه نمی‌دهد. یک دور ممکن است به‌علت timeout یا تعداد زیاد لینک‌ها بیش از فاصلهٔ انتخاب‌شده طول بکشد؛ دور بعدی پس از پایان دور فعلی آغاز می‌شود و تضمین دقیق real-time وجود ندارد. Windows در این تغییر از URL تست Real Ping تنظیم‌شده در v2rayN استفاده می‌کند و fallback دوگانهٔ Android را اضافه نکرده است.

## تعریف رفتار هدف Windows

### صفحه و بخش‌های رابط

- بخش **پایش لینک‌ها**: فهرست همهٔ پروفایل‌ها، آخرین تأخیر، آخرین زمان تست، وضعیت، تعداد خطاهای متوالی، زمان‌بندی، آستانهٔ خطا، شروع/توقف پایش و هشدارها.
- بخش **اتصال Windows**: انتخاب یک پروفایل برای استفادهٔ شخصی از سیستم، به‌علاوهٔ System Proxy و TUN.
- در متن UI صریحاً نوشته شود که تست سلامت هر لینک مستقل از اتصال سراسری Windows است.

### رفتار پیش‌فرض پیشنهادی

| تنظیم | مقدار پیش‌فرض |
|---|---|
| فاصلهٔ پایش | ۲۰ ثانیه |
| آستانهٔ قطع | ۲ شکست متوالی |
| URL اصلی | `https://www.google.com/generate_204` |
| URL جایگزین | `https://www.gstatic.com/generate_204` |
| روش | درخواست HTTPS از مسیر outbound همان پروفایل، نه TCP connect به host:port |
| هم‌زمانی | محدود و قابل‌کنترل؛ دور جدید تا پایان دور قبلی شروع نشود |
| هشدار | یک هشدار هنگام ورود به Disconnected و یک هشدار هنگام بازگشت به Connected |

این مقادیر باید تنظیم‌پذیر باشند. تعداد پروفایل‌ها، timeout و fallback می‌توانند باعث شوند یک دور بیش از ۲۰ ثانیه طول بکشد؛ نباید دورها روی هم انباشته شوند یا زمان‌بندی به‌عنوان تضمین دقیق real-time معرفی شود.

## معیار پذیرش Windows

1. چند لینک از نوع‌های پشتیبانی‌شده و یک لینک نامعتبر وارد شوند.
2. با شروع پایش، هر لینک جداگانه از outbound خودش تست شود؛ فعال/غیرفعال بودن System Proxy و TUN نتیجهٔ تست را تغییر ندهد.
3. لینک سالم به Connected همراه با زمان تأخیر برسد.
4. لینک خراب پس از تعداد شکست تنظیم‌شده Disconnected شود و فقط یک هشدار قطع دریافت شود.
5. با بازیابی لینک، وضعیت به Connected برگردد و یک هشدار بازیابی صادر شود.
6. در طول پایش، System Proxy/TUN و پروفایل انتخاب‌شده برای ترافیک عادی ویندوز ناخواسته تغییر نکنند.
7. با توقف پایش، timer و تست در حال اجرا لغو شوند؛ با بسته‌شدن برنامه هیچ حلقهٔ یتیمی باقی نماند.
8. تست با برنامهٔ minimize شده/tray، راه‌اندازی مجدد برنامه و تعداد زیاد پروفایل‌ها انجام شود.
9. credentialهای لینک در log/notification عمومی چاپ نشوند.

## وضعیت این بازبینی

این سند نتیجهٔ بازبینی سورس Android 0.2.1 و upstream ویندوز 7.25.6 است. اصلاح `BindingRoot` در شاخهٔ توسعه انجام شده و CI آن موفق بوده است. در ادامه، یک پیاده‌سازی اولیه برای پایش دوره‌ای Windows به داشبورد افزوده شده است: زمان‌بندی ۲۰/۳۰/۶۰/۱۲۰ ثانیه، آستانهٔ ۱ تا ۳ خطای متوالی، وضعیت سلامت هر پروفایل و اعلان سینی هنگام قطع/بازیابی. این پیاده‌سازی با موتور Real Ping خود v2rayN کار می‌کند و System Proxy/TUN را برای تست تغییر نمی‌دهد.

آخرین commit توسعه (`d98d1c2de87636fb0a37807062b7ad3577b31011`) در GitHub Actions با موفقیت کامل Build و بسته‌بندی شده است. هر دو Job سبز شده‌اند و Artifact پیش‌نمایش یکپارچه تولید شده است. بااین‌حال CI فقط کامپایل و بسته‌بندی را تأیید می‌کند؛ دریافت واقعی اعلان tray، صحت نتیجهٔ لینک‌ها و زمان‌بندی باید روی Windows 10/11 واقعی آزمایش شوند. نسخهٔ Windows هنوز معادل سرویس مستقل Android نیست: پایش تا وقتی برنامه باز است کار می‌کند و بعد از خروج کامل متوقف می‌شود.
